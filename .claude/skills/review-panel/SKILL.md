# Ревью PR: уровень по путям, `/code-review`, двое проверяющих и панель из пяти

> Последняя сверка: 2026-11-14

Правила — [docs/private/agent-rules.md](../../../docs/private/agent-rules.md), раздел «Ревью PR». Этот навык —
порядок действий. Расходятся — прав agent-rules, а навык правится в том же PR.

## 1. Подготовка

1. `git fetch origin main && git merge origin/main` в ветку PR — проверяем то,
   во что PR вольётся. Чужую ветку не перебазируем.
2. Написать **простыми словами**, что PR делает и зачем, в 3–6 строк. Не
   пишется коротко — PR делает слишком много, сказать об этом.
3. `./build.sh --check` — зелёный. Ровно это гоняет CI; туда же входит сверка
   правил уровней (`tools/review-tier.sh --self-test`).

## 2. Уровень ревью

`tools/review-tier.sh --action` — уровень по путям изменённых файлов,
`--explain` — по файлам и сработавшим правилам. Правила — `tools/review-tier.rules`.
Уровень PR — наибольший из уровней его файлов.

| уровень | что меняется | что делаем | примеры |
|---|---|---|---|
| 0 | только документы, лента «Что нового», версии, карта проекта, тесты без кода модуля, `.gitattributes`, стенд без изменения модуля | ревью нет: основная проверка (`./build.sh --check`) | правка главы справки, строка в CHANGELOG, подъём версии, новый тест |
| 1 | мелкое поведение: всё, что не 0 и не 2 | `/code-review medium --max-findings 5`. Уровень пишем явно: скилл запоминает прошлый. `max` и `ultra` запрещены | исправление в одном классе, текст интерфейса, новая настройка без денег и прав |
| 2 | деньги, лицензия, безопасность, установщик, сборка, CI, Dockerfile и образы, публичный API, схема таблиц | двое проверяющих параллельно, панель из пяти — только при деньгах и лицензиях (п. 3); `/code-review` не зовём | расчёт квоты или цены, проверка лицензии, токен и права, установщик, `Dockerfile`, публичный API, новая таблица |

- В этом модуле уровень 2 — сборка и CI (`build.sh`, `composer.json`, `.github/*`); установщик, перенос
  данных и доведение после обновления копированием (`install/*`, `lib/main/{migration*,setup,maintenance}.php`,
  `lib/core/*`, `lib/container.php`, `lib/analysis/runner.php`, `lib/agent/*`); поля «AI: …» и защита
  (`lib/deal/field/*`); публичный API и безопасность (`lib/controller/*`, `lib/integration/rest/*`,
  `lib/rest/*`, `settings/ajax.php`, `settings/component.php`); схема таблиц (`lib/*/model/*table.php`);
  `.settings.php`, `default_option.php`. Страницы и тексты — уровень 1. Точный список — `tools/review-tier.rules`.
- **Ручной уровень** главнее автоматического. Его задаёт слово владельца («уровень 2», «панель», «без ревью»)
  или строка «Уровень ревью: N» в описании PR: тогда `tools/review-tier.sh --level N --action` (или
  `REVIEW_TIER=N`). Вывод показывает оба: «вручную N, по путям M». Легенда уровней — `tools/review-tier.sh --levels`.
- Агент вправе **поднять** уровень сам: сомнение; правка выросла из рассуждения, а не из замера; в тексте
  цена или условия лицензии. **Понизить** вправе только владелец: ручной уровень ниже автоматического
  печатает предупреждение.
- Пути с пометкой «слово владельца» (`hold` в правилах) меняются только по слову владельца.
- Какая модель и усилие у агентов, сколько исполнителей — режим «экономия» или штатный,
  раздел «Ревью PR» в agent-rules.

## 3. Ревью уровня 2 — агенты одним сообщением, параллельно

Двое: **Безопасность** и **Инженер/QA** (роли «Инженер» и «QA» таблицы — в одном агенте). Пятеро — только
если PR трогает деньги или лицензии: все роли таблицы, по агенту на роль.

| роль | модель, усилие | смотрит |
|---|---|---|
| **Документация** (только в панели из пяти) | Sonnet, среднее | `docs/guide`, `docs/dev` (событие `OnAfterCrmWrite`, REST и MCP), `docs/private/project-map.md`, `CLAUDE.md`, `README.md`, `CHANGELOG.md`, лента `changelog/`, пакет `kb/guide`, навыки: верно ли против кода, сверена ли документация с правкой (agent-rules, п. 4), открываются ли ссылки, совпадают ли якоря `settings/faqdata.php` с заголовками глав; тексты для людей — настоящее время, «AI», без названия модели, цен и сравнений |
| **Инженер** | Sonnet, среднее | верность решений; канон линейки (`lib/` строчными, установщик, `strict_types`, `install/layout.php`); шов к shef.toolsai — только публичный API (`tests/seam_test.php`); перенос данных (`Main\Migration`: сверка перед отметкой, повтор безопасен); агенты — по одному на тип; опоры на ядро — с `файл:строка` ядра портала |
| **QA** | Sonnet, среднее | краснеет ли тест, если сломать код (`tests/*_test.php`); всё ли заявленное в PR проверено; что можно проверить только на стенде (поля и кнопки в карточке, робот БП, перенос данных на портале с данными shef.toolsai, обновление копированием) — так ли и названо |
| **Безопасность** | Sonnet, среднее; в панели из пяти — Opus, высокое | права разделов (`lib/settings/sectionaccess.php`: администратор и действия ролей shef.toolsai); контроллеры (`lib/controller/*`: право в каждом действии, фильтры, CSRF); `settings/ajax.php` и `settings/component.php`: сессия, экранирование; запись в CRM без проверки прав — только из модуля (`CrmWrite`); REST и MCP (`lib/integration/rest/*`: право того, кто спрашивает); перенос данных — SQL без подстановки ввода; личные данные в журналах и событии `OnAfterCrmWrite` |
| **CTO** (только в панели из пяти) | Opus, высокое | изменение целиком: объём, цена, направление, что оно обещает линейке и порталу клиента; данные порталов (коды настроек и отметок); не решение ли это владельца (agent-rules, п. 6) |

Модель — параметр запуска агента. Усилие — как позволяет среда запуска; **максимум усилия — никогда**.

Каждому в задании — дословно по смыслу:

- Проект большой. Начни с `git diff origin/main...HEAD --stat`, читай по делу,
  не грузи всё дерево, не упади по таймауту.
- Дерево общее. Чужая правка — сосед, не откатывать и не строить на ней теорий.
- Код меняет только QA (в паре — «Инженер/QA») и только чтобы проверить, что тест
  краснеет, — в отдельном `git worktree`, мутаций не больше 3 на PR. Откат мутации —
  из копии во временном каталоге, **никогда** `git checkout --`.
- Ядро Битрикса и REST сверять с источником (agent-rules, п. 1; `.bitrix-docs/` — `CLAUDE.md`,
  «Документация и практики Битрикс»), не по памяти.
- Ключи, вебхуки и данные клиентов в отчёте не цитировать.
- Сообщать находки: файл:строка, что, почему важно, как чинить, насколько
  уверен. Не чинить.

## 4. Отчёт владельцу — по-русски, коротко

Блок на проверяющего: **кто — что — почему важно — как чинить**. Без
стенограмм. Отдельно — что берёшь в работу и что нет, с причиной и замером.

## 5. Исправления и повтор

- Всё — **в этом же PR**. Просится в отдельный issue или PR — не выносить
  молча, сказать и обсудить.
- Исправленный гард — с тестом, который краснеет при мутации (agent-rules, п. 5).
- После правок: `./build.sh --check`, пуш. Перепроверяет **только нашедший**
  замечание — продолжением того же агента (сообщением ему), а не новым.
- Ревью заново целиком — только если PR переписан. Серия связанных PR — **одно ревью
  (двое или панель) на общий дифф** серии, а не по ревью на каждый PR.
