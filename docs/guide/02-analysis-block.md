# Общий блок анализа сущности

> Последняя сверка: 2026-11-09

## Что и зачем

Один и тот же блок анализа разбирает сделку, лид и элемент
смарт-процесса, а поведение настраивается промптом.

**Один код, без двух путей.** Сделка не идёт своим путём:
у неё нет своей обёртки полей, своей таблицы проверок и своего агента.
Сделка — просто один из типов. То, что у сделки действительно своё
(откаты по стадиям, флаг `CLOSED`, ключ воронки карточки), описано как
**возможность типа** в `EntityType`, а не как ветка «если сделка».

Что в блоке общее для всех типов:

* риск, «почему», «что сделать» — поля `UF_SHEF_AI_*`;
* кнопки «Риск под контролем» и «Отработано», флажки для фильтра;
* сброс отметок при смене зоны шкалы;
* шкала профиля: дело ответственному, комментарий в таймлайн, дело
  старшему, «старшего не привлекаем»;
* поля в карточке — раздел «AI-анализ»;
* история риска ([История риска](04-risk-history.md)) и шаблон промпта ([Промпты анализа](05-analysis-prompts.md)).

## Тип сущности

`Analysis\EntityType` — чистое описание, без ядра:

| | Сделка | Лид | Смарт-процесс |
|---|---|---|---|
| entityTypeId | 2 | 1 | свой (обычно от 128) |
| ENTITY_ID полей | `CRM_DEAL` | `CRM_LEAD` | `CRM_{ID типа}` |
| Воронки | направления | нет (одна, 0) | если включены в типе |
| Ключ карточки | `deal_details_c_{N}` | `lead_details` | `DYNAMIC_{entityTypeId}_details_C{N}` |
| Стандартный промпт (`promptKind()`) | `deal` | `lead` | `dynamic` |
| Откаты по стадиям (`stageRollbacks`) | да | нет | нет |
| Флаг `CLOSED` в выборке (`closedFlag`) | да | нет | нет |
| Ключ воронки карточки (`cardCategoryExtra`) | `DEAL_CATEGORY_ID` | — | `CATEGORY_ID` (если есть воронки) |

Тип клиента (по компании, иначе по контакту) — не возможность типа, а
поля записи: есть у записи `COMPANY_ID` и `CONTACT_ID` — модуль его
считает (`Deal\ContextBuilder`, `Item::hasField()`).

**Осторожно с ENTITY_ID смарт-процесса.** Число в `CRM_{…}` — это ID
записи типа (`b_crm_dynamic_type.ID`), а не entityTypeId. Модуль берёт его у фабрики:
`Factory::getUserFieldEntityId()`.

Ключ карточки модуль не собирает сам — спрашивает ядро
(`Crm\Entity\EntityEditorConfig::getConfigId()`). Воронку ядро читает из `CATEGORY_ID`.

## Из чего состоит

| Класс | Что делает |
|---|---|
| `Analysis\EntityType` | описание типа (чистое) |
| `Analysis\EntityTypes` | типы из CRM: сделка, лид, смарт-процессы портала |
| `Analysis\EntityFields` | поля: создать, записать (через `CrmWrite`), положить в карточку, удалить |
| `Analysis\CrmWrite` | одна запись модуля в CRM: режим по настройке `DEAL_crmevents`, событие `OnAfterCrmWrite` |
| `Analysis\CheckStore` | «последняя проверка» любого типа — одна таблица `shef_toolsaicrm_entity_check` |
| `Analysis\Candidates` | кандидаты любого типа через фабрику |
| `Analysis\Runner` | один проход по записям типа |
| `Agent\AnalysisAgent` | агент одного типа: свой интервал, лимит и блокировка |
| `Deal\ContextBuilder` | сводка для модели — с типом сущности |
| `Analysis\TimelineSource`, `Analysis\Timeline` | история записи: касания по времени для сводки ([Анализ сделок](01-deal-analysis.md#история-записи)) |
| `Analysis\RecordHistory` | та же история наружу — чату справа и MCP, с правами CRM |
| `Deal\Escalation` | дела и комментарии — к нужной сущности |

События полей — `EntityFields::EVENTS`; проверки всех типов, и сделок тоже, лежат в одной таблице.

## Агенты: по одному на тип

У каждого типа **свой агент** Битрикса —
`\Shef\ToolsAiCrm\Agent\AnalysisAgent::run(<entityTypeId>);`: сделки — `run(2)`,
лиды — `run(1)`, смарт-процесс — `run(<его entityTypeId>)`. Зачем: лиды и
смарт-процессы не ждут, пока сделки съедят общий лимит, а
частоту каждого типа можно настроить отдельно.

| Что | Где задаётся | По умолчанию |
|---|---|---|
| интервал | «Авто-анализ CRM» -> «Агенты анализа», настройка `ANALYSIS_interval_{тип}` (минуты) | `DEAL_interval` — 60 минут |
| анализов за прогон | там же, `ANALYSIS_maxperrun_{тип}` | `DEAL_maxperrun` — 50 |
| блокировка | группа `shef.toolsaicrm.analysis.{тип}` | — |

Агентов заводит и снимает «Проверить и включить»
(`Main\Setup::ensureAnalysisAgents()`): агент есть у каждого типа с
включённым профилем; профиль выключили — агент снимается. Повторный
запуск ничего не дублирует. Сохранение на странице «Агенты анализа» и
сохранение профиля сверяют агентов сразу: первый включённый профиль
типа заводит его агента. Профили не прочитались (сбой базы) — «Проверить и
включить» агентов не трогает и пишет об этом в отчёте.

Двойной обработки нет: у агента и ручного прогона типа одна блокировка,
у каждой записи — строка проверки, повтор не раньше `REANALYZE_DAYS`
профиля. Провайдер лежит или квота кончилась — прогон типа
останавливается.

**Расход.** Лимит 50 — у каждого типа свой.
Включили профили лидов и двух смарт-процессов — за час может уйти до
4 × 50 запросов. Нужен меньший расход — уменьшите лимит типов.

## Поля «AI: …»

У каждого поля в карточке — штатная подсказка «?» (`HELP_MESSAGE`): что значит поле и
кто его пишет. Поле без подсказки получает её при прогоне агента.

Поля (`UF_SHEF_AI_*`: риск, следующий шаг, история, отметки) создаёт «Проверить и включить» — и, сам агент анализа перед проходом по записям: если у типа с включённым профилем полей нет (кнопку забыли после установки, новый смарт-процесс, поле удалили руками), недостающие создаются; существующие не трогаются. Не удалось — предупреждение в журнал shef.problems, анализ идёт, в карточку не пишется (причина в отчёте: «поля «AI: …» не созданы»). Новый смарт-процесс получает поля при первом прогоне агента после включения профиля для его типа.

У существующих полей модуль дописывает пустые названия и подсказки, подписи администратора не трогает. Если конвертация лида создала в сделке дубли «AI: …» с кодами `UF_CRM_…`, удалите их в настройках полей сделки: модуль в них не пишет, их заполняет штатный AI Битрикс24.

## Почему запись пропущена

Пропуск без модели (тишина меньше порога профиля или не о чем рассуждать)
записывается одним и тем же текстом для всех типов: в историю проверок и в
последние проверки агента (раздел «Авто-анализ CRM»). Текст понятный и с
цифрами — сколько дней назад была последняя активность, какой порог в профиле,
до какого числа запланировано дело. Слово — по типу: «сделка», «лид», элемент
смарт-процесса. Если оценивать нечего (нет звонков, комментариев, писем и
откатов), в поля записи пишется риск -1 и причина — для всех типов одинаково;
пропуск по тишине поля не трогает. Подробности и примеры — [Анализ сделок](01-deal-analysis.md), раздел
«Дешёвый фильтр до модели».

## Последние проверки агента

Раздел «Авто-анализ CRM» (`/shef/toolsaicrm/?section=profiles`), под
агентами — блок «Последние проверки агента — 20 последних». Это не весь список, а последние 20 проверок **выбранного типа**:
вкладка на каждый тип, у которого есть профиль, — «Сделки», «Лиды»,
«Смарт-процесс „…“». Один тип — без вкладок, только его название.

Источник — таблица `shef_toolsaicrm_entity_check` (одна строка на запись —
её последняя проверка), фильтр по `ENTITY_TYPE_ID`, сортировка по времени
проверки. Колонки: запись (номер со ссылкой на карточку), время, риск,
почему, что сделано ([Анализ сделок](01-deal-analysis.md), «Что сделано»). Риск «—» —
пропуск без модели, «−1 (оценить нечего)» — оценивать было нечего, «⚠» —
нужен старший.

По умолчанию в блоке **только проверки моделью** — записи с
оценкой риска, где модель что-то сказала. Пропуски без модели (запись в
работе, оценить нечего) прячет ссылка «Показать и пропуски» — их обычно
большинство, и проблемы за ними не видно. В «Что сделано» вместо повтора
причины из «Почему» пишется просто «ничего». Номер записи открывает её
карточку штатным слайдером CRM поверх портала.

Ссылку на карточку даёт штатный роутер CRM
(`Service\Router::getItemDetailUrl()`), поэтому она верна и для сделки, и
для лида, и для смарт-процесса, и при новых адресах карточек. Не ответил
роутер — запасной адрес: `/crm/deal/details/N/`, `/crm/lead/details/N/`,
`/crm/type/<тип>/details/N/`. Порядок вкладок, выбор вкладки и адрес —
чистый класс `Analysis\LastChecks` (тест `tests/lastchecks_test.php`).

## Защита полей от правки

| | Сделка | Лид | Смарт-процесс |
|---|---|---|---|
| `EDIT_IN_LIST = N` | да | да | да |
| `onGetPublicEdit` — просмотр вместо редактора | да | да | да |
| откат правки не модулем | `OnBeforeCrmDealUpdate` | `OnBeforeCrmLeadUpdate` | **нет** |

У смарт-процессов совместимого события «до изменения» в ядре нет. Поэтому
REST или робот может переписать их поля «AI: …». Следующий анализ всё
равно запишет свои значения.

**Запись из лида**: при конвертации наши поля лида очищаются в
новой сделке (`OnBeforeCrmDealAdd`, до записи) и в элементе
смарт-процесса (`onCrmDynamicItemAdd`, сразу после) — подробно в
[Лиды и смарт-процессы](03-leads-smart.md). Защите это не мешает: она срабатывает только на
изменение.
